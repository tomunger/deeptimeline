# Deep Time Line

A vertical, zoomable timeline of the whole history of Earth — geological,
biological, and cultural events on one continuous linear scale, from the
formation of the planet at the top to the present at the bottom.

The point is to make the *proportions* of history legible: how long the Earth
has been here, how recent human civilization is, and how fast the last few
centuries have moved.

## Overview

**Layout.** Four columns beside the time axis:

| Column | Contents |
|---|---|
| Cultural | Actions taken by conscious, sentient beings |
| Biological | Evolution of species and information about them |
| *Time axis* | Dates and tick marks |
| Geological | What the Earth itself was doing |
| Geological time scale | Eon / era / period / epoch / age, in official ICS colours |

**Zoom.** Level 1 shows the entire 4.54-billion-year span; each level halves the
visible span down to about one year (~33 levels). Events carry an *importance*
tier that maps to the coarsest zoom at which they appear, so detail thickens as
you zoom in rather than all arriving at once. The GTS columns re-flow as you
zoom — a column holding a single long span renders its label vertically and
narrows; columns whose divisions are too short to label collapse.

Also: full-text search over event names and tags, tag filtering, a scrollbar
showing where you are in time, and Markdown popups with links to sources.

**Data model.** Events are plain JSON records: name, category, start (and
optional end) year, a `precision` that governs both formatting and implied
uncertainty (`mya` … `datetime`), an importance tier, tags, a Markdown
description, and links. Years are stored as astronomical year numbers on a
single float64 axis, which covers billions of years and exact modern dates alike.

**Data pipeline.** `data/` is the authoring source of truth. The ingest CLI
validates it against the schema and publishes it to `apps/web/public/data/`,
which the app fetches at runtime:

```
data/{gts,events}.json  --(npm run ingest: validate)-->  apps/web/public/data/{gts,events}.json
```

`data/tags.json` is a controlled vocabulary — ingest rejects any event tag not
defined there, so tags stay typo-free. `data/gts.json` (~171 ICS intervals) is
generated by `apps/ingest/src/gen-gts.ts`; edit the generator, not the JSON.
Never edit `apps/web/public/data/` directly — it is generated and gitignored.

**Stack.** TypeScript throughout, React 18 + Vite for the frontend, npm
workspaces monorepo, no backend — the production artifact is a static site
served by nginx. `packages/shared` holds the types, time math, and GTS colours;
`apps/web` is the UI; `apps/ingest` is the validate-and-publish CLI.

See [doc/architecture.md](doc/architecture.md) for the full structure, the
compilation model, and the reasoning behind the static-data design.

## Running locally

Requires **Node 22 or newer** (the Docker build uses `node:22-alpine`) and npm.

```bash
git clone https://github.com/tomunger/deeptimeline.git
cd deeptimeline
npm install     # installs every workspace into one hoisted node_modules
npm run dev     # runs ingest, then starts Vite
```

Open <http://localhost:5173>.

| Command (from repo root) | Effect |
|---|---|
| `npm install` | Install all workspaces |
| `npm run dev` | Ingest, then start the dev server |
| `npm run ingest` | Validate `data/` and publish to `apps/web/public/data/` |
| `npm run build` | Ingest, type-check, then build `apps/web/dist/` |
| `npm run typecheck` | Type-check every workspace |
| `npm test` | Run unit tests (`packages/shared`) |

**Editing events while the server runs.** Ingest is *not* part of Vite's watch,
so a change to `data/events.json` will not hot-reload. Run `npm run ingest` in a
second terminal and refresh, or restart `npm run dev`. If a record is invalid,
ingest prints every error and writes nothing — the previous published data stays
in place.

To preview the real production bundle instead of the dev server:

```bash
npm run build
npm run preview --workspace apps/web
```

## Versioning and pushing to GitHub

**Versions are git tags.** The `version` fields in the `package.json` files are
unused placeholders; the release version is whatever `vMAJOR.MINOR.PATCH` tag
you push. [`.github/workflows/docker.yml`](.github/workflows/docker.yml) builds
and pushes an image to GitHub Container Registry on every push to `main` and on
every `v*` tag.

Image tags produced at `ghcr.io/tomunger/deeptimeline`:

| Trigger | Tags written |
|---|---|
| Push to `main` | `latest`, `sha-<short-sha>` |
| Push tag `v1.4.2` | `1.4.2`, `1.4`, `1`, `sha-<short-sha>` |

Ordinary change:

```bash
npm run build          # confirm it compiles and the data validates
git add -A
git commit -m "Describe the change"
git push origin main   # -> rebuilds :latest
```

Cutting a release:

```bash
git tag -a v0.2.0 -m "Human evolution events"
git push origin v0.2.0
```

Then watch the run under the repo's **Actions** tab, and confirm the new tags
under **Packages**. Rough guide for the number: **patch** for fixes and
data corrections, **minor** for new events or features, **major** for a change
that breaks the data schema or the deployment contract.

Note that the data is **baked into the image** — the Dockerfile runs ingest at
build time — so adding events means building and deploying a new image, not just
uploading JSON. (The architecture doc describes a future split where data
publishes independently; that is milestone M6 and is not built yet.)

One quirk worth knowing: the existing `v0.1.0` tag was cut *before* the semver
tag patterns were added to the workflow, so GHCR currently holds only `latest`
and `sha-…` tags. The next `v*` tag you push will be the first to produce
version-numbered images.

## Installing on Unraid

The image is public, so no registry credentials are needed.

**Option A — use the bundled template (recommended).** Copy
[`deploy/unraid/deeptimeline.xml`](deploy/unraid/deeptimeline.xml) onto the
Unraid box, then add the container from it:

1. From a machine with the repo checked out:
   ```bash
   scp deploy/unraid/deeptimeline.xml \
     root@<unraid-host>:/boot/config/plugins/dockerMan/templates-user/
   ```
2. In the Unraid web UI go to **Docker → Add Container**.
3. Set the **Template** dropdown to **DeepTimeline** under *User templates*.
   Repository, network, and port are filled in for you.
4. Adjust **WebUI Port** if 8080 is taken on the host, then click **Apply**.

**Option B — add it by hand.** **Docker → Add Container**, leave Template on
*Select a template*, and fill in:

| Field | Value |
|---|---|
| Name | `DeepTimeline` |
| Repository | `ghcr.io/tomunger/deeptimeline:latest` |
| Network Type | `Bridge` |
| WebUI | `http://[IP]:[PORT:80]/` |
| Port (Add another Path, Port, Variable…) | Container Port `80`, Host Port `8080`, TCP |

Apply, and the site is at `http://<unraid-ip>:8080`.

**No volumes, no environment variables, no persistent state** — the container is
an nginx instance serving a static build, and everything it needs is inside the
image.

**Updating.** With `:latest`, the Docker tab shows *update ready* when a new
image is published; **Check for Updates**, then **Apply Update**. If you would
rather move deliberately, change the repository to a pinned version — for
example `ghcr.io/tomunger/deeptimeline:0.2` to track patch releases of 0.2, or
`:0.2.0` to freeze exactly — and edit the tag when you want to move up.
